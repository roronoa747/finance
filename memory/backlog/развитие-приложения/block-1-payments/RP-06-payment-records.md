# RP-06 — Записи платежей и производные остатки (фронт: модель, слияние, математика, стор)

Блок 1 · MVP · Каталог: `frontend/` · Зависит от: Блок 0 · Роли: member

## Контекст (что уже есть)

- Решения: Р-3 (одна механика для всего по графику), Р-4 (кредит: остаток уменьшается на
  тело платежа по аннуитету, разбивку считает `finance.ts`), Р-5 (списание со счёта; по
  умолчанию — счёт прошлой оплаты этого платежа; «не списывать» — исключение), Р-7 (записи с
  id, объединение по id, остатки выводятся из записей; один платёж за период — одна отметка;
  снять можно — деньги возвращаются), Р-30 (месяцы по Алматы). Правило новых данных — §6.
- Типы `types/finance.ts`: `Account.amount` — «всегда в тенге», правится напрямую
  (`stores/finance.ts` `setAccountAmount` → `updateAccount`, `:502-518`); `Credit.principal`,
  `payment`, `annualRate`, `day` — правятся `updateCredit` (`:570`), добавляются `addCredit`
  (`:314`); `Obligation` — `versions`, `day`, `every?: 'month'|'year'`, `month?` (1–12 для
  годовых), `who?`, `parentId?`.
- Сейчас никаких отметок оплаты нет. Взносы в цели — образец append-only списка
  (`Goal.movements`, `mergeGoal` в `lib/merge.ts`).
- `finance.ts`: `annuityMonths`, `debtCost` (`monthlyInterest` = principal × rate / 12, в
  дробях), `amountAt(o, key)`, `dueIn(o, key)`, `untilPayday(state, now = today())`
  (`:537-600`: ближайшая зарплата, платежи до неё, деньги на не-депозитных счетах, нехватка).
  Разбивки платежа на тело/проценты нет.
- Стор: `accounts` = `householdAccounts` + `privateAccounts` (личные — в `privateDoc`);
  `credits`, `obligations` — из `householdDoc`. Вью читают `acc.amount`, `c.principal`
  напрямую (Capital, GoalDetail, Overview, Ritual, Setup).
- `lib/dates.ts`: `monthKey(d = new Date())`, `today()` — по времени устройства.

## Задача

1. **Время по Алматы (Р-30):** в `lib/dates.ts` — «сегодня» и ключ месяца по Asia/Almaty
   (UTC+5 фиксированно, как `backend/internal/fx`). Решить, переводить ли `today()`/
   `monthKey()` без аргумента на Алматы целиком (предпочтительно — одна правда) или завести
   отдельный хелпер; решение и затронутые места — в Handoff.
2. **Модель:** список верхнего уровня `SyncDoc.payments` — записи (`Tracked` + `id`):
   что оплачено (`kind`: обязательство / кредит / досрочка — досрочку использует RP-08),
   `targetId`, период (`YYYY-MM` месяца списания; для годовых — их месяц), `amount` (целое,
   сколько списано), для кредита — `principal` (целое тело, снимок на момент отметки),
   `accountId` (`null` — «не списывать»), `by`, `at`. Точные имена полей — на исполнителе,
   с JSDoc «зачем», как у соседних типов. Добавить в `defaultSyncDoc()` и **явно** в
   `mergeDocs` (по id, надгробия).
3. **Якорь ручной правки остатка:** счёт и кредит получают отметку времени последней ручной
   установки остатка (`setAccountAmount`, `addAccount`; `addCredit`, `updateCredit` при смене
   `principal`). Запись влияет на остаток, только если сделана **после** якоря (нет якоря —
   влияет). Так ручная сверка с банком не удваивает уже учтённые отметки.
4. **`finance.ts` (все числа — здесь, результат в целых тенге):**
   - разбивка очередного платежа кредита на проценты и тело (Р-4); последний платёж — не
     больше остатка + проценты;
   - производный остаток счёта (база − списания + возвраты по живым записям после якоря) и
     производный остаток кредита (база − тело по живым записям после якоря);
   - «оплачено ли за период» и дедупликация: несколько живых записей на одну пару
     (цель, период) — учитывается одна (ранняя по `at`, при равенстве — меньший `id`),
     остальные не влияют ни на что (Р-7: повтор с другого устройства не удваивает);
   - следующий платёж цели (дата + сумма) с учётом отметок и `dueIn`/`every`;
   - `untilPayday` — по производным остаткам, уже оплаченное в периоде не входит в
     «до зарплаты» (Р-5 «честный остаток»).
5. **Стор:** все чтения остатков (`accounts`, `householdAccounts`, `privateAccounts`,
   `credits`) отдают производные значения — экраны не меняются; запись остатка
   (`setAccountAmount` и др.) ставит базу **и** якорь. Действия: отметить (сумма по
   умолчанию — из графика, счёт по умолчанию — из прошлой записи той же цели, Р-5), снять
   отметку (надгробие на все живые записи пары; повторная отметка — новая запись с новым id).
   Личный счёт: запись в общем документе ссылается на `accountId` личного счёта — остаток
   считается на устройстве владельца; у партнёра такой id просто не находится (не ошибка).
6. Комментарий в `types/finance.ts` у `payments` — почему записи, а не перезапись (две
   офлайн-отметки, Р-7) — в стиле соседних комментариев.

## Тесты

- `lib/finance.test.ts`: разбивка аннуитета — сумма тела по графику = исходный долг (с
  точностью до округления в последнем платеже), всё в целых; производные остатки счёта и
  кредита; якорь (запись до якоря не влияет); дедупликация пары; снятие (надгробие)
  возвращает деньги; следующий платёж для ежемесячного, годового и кредита;
  `untilPayday` без оплаченного.
- `lib/merge.test.ts`: две офлайн-отметки разных платежей с двух клиентов → обе; одна пара с
  двух клиентов (разные id) → после слияния две записи, остаток уменьшен один раз.
- `e2e/two-clients-sync.test.ts` (или файл Блока 1): A отмечает аренду офлайн, B — кредит
  офлайн → оба синкают → у обоих обе отметки, карта уменьшена на сумму двух.
- Граница месяца по Алматы (23:30 UTC 31-го = уже 1-е по Алматы).

## Критерии приёмки

- Остатки на экранах после отметки сверены с `finance.ts` до тенге (тест + ручная сверка).
- Старые данные без `payments` и якорей открываются без изменений цифр.
- `cd frontend && npm run build && npm test` зелёные.

## Вне скоупа

- Кнопки и экраны отметки — RP-07; применение досрочки — RP-08; зарплата — RP-10.
- Перевод взносов в цели на списание со счёта записями (как сейчас: `GoalDetail` правит
  остаток напрямую).
- Валюта у платежей (Р-1, не-скоуп).
