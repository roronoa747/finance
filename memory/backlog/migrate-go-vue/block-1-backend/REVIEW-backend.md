## Находки

### Н-1 · высокая · Несоответствие типов `lib/pq`: `json.RawMessage` передаётся в запрос без явного приведения `::jsonb`

`backend/internal/repository/doc_repo.go:100, 177, 202`. В методах `PushHouseholdDoc` и `PushPrivateDoc` переменная `data` имеет тип `json.RawMessage` (псевдоним для `[]byte`). В драйвере `github.com/lib/pq` значение `[]byte` по умолчанию передаётся в PostgreSQL с OID `17` (`BYTEAOID`). В реальной базе PostgreSQL при выполнении запроса `SET data = $1` без явного каста возникает ошибка `ERROR: column "data" is of type jsonb but expression is of type bytea`. В мок-репозитории тесты зелёные, но на реальном PostgreSQL запись бюджета или приватного кошелька упадёт с ошибкой 500.

**Рекомендация.** В SQL-запросах `PushHouseholdDoc` и `PushPrivateDoc` добавить явное приведение типов: `SET data = $1::jsonb` и `VALUES ($1, $2, 1, $3::jsonb)` или передавать `string(data)`.

### Н-2 · высокая · Неатомарное создание пользователя и домохозяйства при регистрации (`Register`)

`backend/internal/handlers/auth.go:71-86`. Регистрация пользователя состоит из двух последовательных вызовов разных репозиториев: `userRepo.Create(...)`, затем `householdRepo.CreateHousehold(...)`. Если второй шаг завершается ошибкой (сетевой сбой, падение БД, ошибка валидации имени), в таблице `users` остаётся «осиротевшая» запись пользователя без домохозяйства. Повторная регистрация блокируется ошибкой `409 Conflict (user already exists)`, а логин через `authHandler.Login` завершается ошибкой `ErrMembershipNotFound` -> `500 Internal Server Error`. Пользователь навсегда теряет доступ к аккаунту.

**Рекомендация.** Выполнять создание пользователя и домохозяйства в рамках единой транзакции БД (или добавить компенсирующее удаление пользователя при ошибке инициализации домохозяйства, либо в `Login` корректно обрабатывать случай отсутствия членства).

### Н-3 · средняя · Состояние гонки при одновременном присоединении к семье: отсутствие блокировки строки домохозяйства

`backend/internal/repository/household_repo.go:271-308`. В методе `JoinHousehold` транзакция блокирует запись инвайта (`FOR UPDATE`), однако выбор свободного слота ('a', 'b', 'c') выполняется обычным `SELECT slot FROM household_members WHERE household_id = $1`. Если к домохозяйству параллельно присоединяются два участника (по разным инвайтам или при повторных запросах), оба считывают одинаковый набор занятых слотов, оба претендуют на слот `'b'`, и один из запросов завершается падением с ошибкой нарушения ограничения уникальности `UNIQUE (household_id, slot)` -> HTTP 500.

**Рекомендация.** В начале транзакции `JoinHousehold` блокировать родительскую строку домохозяйства: `SELECT id FROM households WHERE id = $1 FOR UPDATE`, что обеспечит строгую последовательность назначения слотов.

### Н-5 · средняя · Отсутствие валидации пустого `HouseholdID` в защищённых эндпоинтах

`backend/internal/handlers/sync.go:31, 53, 97, 119`, `backend/internal/handlers/household.go:46`. Функция `auth.GetHouseholdID(r.Context())` возвращает `string, bool`. Если токен содержит пустую строку `HouseholdID` (например, при некорректном выпуске токена или ручном токене), условие `if !ok` не срабатывает, и пустая строка передаётся в SQL-репозиторий. В PostgreSQL запрос с пустым UUID приводит к ошибке `invalid input syntax for type uuid: ""` и ответу `500 Internal Server Error` вместо контролируемого `401 Unauthorized` / `400 Bad Request`.

**Рекомендация.** Заменить проверку на `if !ok || strings.TrimSpace(householdID) == ""` во всех хендлерах синхронизации и инвайтов.

**Вердикт: клинап**

### Н-6 · средняя · Игнорирование сбоев раннера миграций в `main.go` и отсутствие `pg_advisory_lock`

`backend/cmd/server/main.go:52-54`, `backend/internal/db/migrate.go:57-75`. При возникновении ошибки в `db.RunMigrations` сервер лишь выводит сообщение `log.Printf("warning: migration runner encountered an error: %v", err)` и продолжает запуск. В продакшене это приведёт к запуску сервиса на неполной схеме базы. Кроме того, при горизонтальном масштабировании (запуск нескольких реплик сервиса) одновременное применение миграций без блокировки на уровне Postgres может вызвать гонки создания таблиц.

**Рекомендация.** В `main.go` прерывать запуск `log.Fatalf` при ошибке миграций, если задан `DATABASE_URL`; в `RunMigrations` добавить захват advisory lock (`SELECT pg_advisory_lock(hashtext('migrations'))`).

### Н-7 · низкая · Отсутствие лимита размера тела запроса (`http.MaxBytesReader`)

`backend/internal/handlers/sync.go:66, 132`, `backend/internal/handlers/auth.go:53, 106`. Обработчики читают `r.Body` без ограничения входящего размера данных. В эндпоинтах синхронизации передачи полного JSON бюджета (`/api/sync/household`, `/api/sync/private`) злоумышленник или сбойный клиент может передать тело объёмом в сотни мегабайт, спровоцировав OOM-kill сервера.

**Рекомендация.** Ограничить входящий поток через `r.Body = http.MaxBytesReader(w, r.Body, 10<<20)` (10 МБ для синхронизации, 1 МБ для авторизации).

### Н-9 · низкая · Риск блокировки браузером при `CORSOrigin: *` с `AllowCredentials: true`

`backend/internal/config/config.go:22`, `backend/cmd/server/main.go:120`. По умолчанию `CORSOrigin` имеет значение `"*"`. При наличии флага `AllowCredentials: true` стандарт Fetch API запрещает ответ `Access-Control-Allow-Origin: *` при запросах с учетными данными. Кроме того, при локальной разработке Vite может занимать порты 5173, 5174 или запускаться на `127.0.0.1`.

**Рекомендация.** В `config.go` поддержать список origin (например, через запятую: `http://localhost:5173,http://127.0.0.1:5173`) и по умолчанию разрешать стандартные локальные порты разработки.

### Н-10 · низкая · Отсутствие разделения `/api/health` на liveness и readiness для продакшен-оркестраторов

`backend/internal/handlers/health.go:20-39`. Эндпоинт `/api/health` возвращает статус `200 OK` даже при недоступной БД (`db: "disconnected"`). Для локальной разработки в mock-режиме это удобно, но в Kubernetes / Cloud Run это может помешать корректной работе readiness-пробы.

**Рекомендация.** Зафиксировать хвост на разделение эндпоинтов: `/api/health/live` (200 всегда) и `/api/health/ready` (503 при падении БД в проде).
