## Проверено независимо (не по Handoff-у)

- **JWKS при отмене запроса — воспроизвёл.** Временный тест в пакете (удалён, дерево чистое): `Verify` с контекстом,
  истекающим за 20 мс при ответе ключей за 200 мс → `ErrUnavailable`; **следующий нормальный** `Verify` →
  `keys failed to load a moment ago` (503). Отсюда Н-1.
- **Порядок блокировок** — прочитан по SQL. `JoinHousehold`: приглашение `FOR UPDATE` → семья `FOR UPDATE` → строка
  пользователя. `DeleteAccount`: семьи `FOR UPDATE` → `DELETE household_invites` (строки приглашений). Цикл
  «приглашение ↔ семья» есть. `CreateHousehold` берёт строку пользователя `FOR UPDATE`, удаление её не берёт —
  отсюда 500 по RESTRICT `created_by` (замечание приёмки). Отсюда Н-2.
- **Все FK на `app.users` покрыты удалением** (сверил `000001`–`000006`): `households.created_by` RESTRICT — передача
  наследнику или удаление семьи; `household_members`, `private_docs`, `household_invites.created_by`,
  `statement_uploads`, `operations`, `photos` — CASCADE и явный `DELETE`; `household_docs.updated_by`,
  `household_invites.used_by`, `events.user_id` — SET NULL. События удалённого обезличиваются — это проверяет
  `events_pg_test.go:103-111`. Значит, замечание приёмки «нет запроса по `events`» снимается: остаётся только
  комментарий (Н-5).
- **Миграции** `000005` (`DROP NOT NULL`, два `ADD COLUMN IF NOT EXISTS`, уникальный индекс) и `000006`
  (`CREATE TABLE/INDEX IF NOT EXISTS`) только добавляют или ослабляют (Р-19). `000004` — из Блока 13, этот блок её
  не менял. `cmd/migrate` ждёт 13 таблиц.
- **Роутер** (`server/server.go:159-220`): все ручки семьи стоят в подгруппе `RequireHousehold`. В проде нет
  `register` (`:171`). `Middleware` подменяет семью, роль и слот из базы и стирает их, если у пользователя нет семьи
  (`auth/middleware.go:67-72`). Значит, ни одна ручка не доверяет семье из токена.
- **`docDataProblem`** (`handlers/sync.go:29-71`): прошёл обход вручную. `data[i+1]` после `\` безопасен (`json.Valid`
  не пропускает `\` последним байтом). Граница пары суррогатов `i+6 >= len` верна, ключи — тоже строки и проверяются.
- **Регион:** функция Vercel — `icn1` (`vercel.json`), база — Сеул. Два запроса резолвера на каждый запрос стоят
  миллисекунды (Н-11).

## Находки

### Н-1 · средняя · Отменённый клиентом вход включает минуту 503 для всех входов на экземпляре

`internal/googleauth/googleauth.go:165-167`. `fetch` ходит за ключами с контекстом запроса. Если клиент закрыл
вкладку или пропала сеть, `fetch` возвращает `context canceled`, и `failedAt = now` взводит минутную паузу
(добавлена критиком). На холодном экземпляре ключей ещё нет (`v.keys == nil`), поэтому каждый вход Google на этом
экземпляре в течение минуты получает 503 «Вход через Google недоступен». На тёплом экземпляре пауза задевает только
незнакомый `kid`: известные ключи отдаются и после сбоя (`:158-161`). Воспроизведено временным тестом (см. выше).
Так можно и нарочно гасить вход: запрос, оборванный сразу после отправки, раз в минуту.

**Рекомендация.** Ключи загружать без отмены запроса: `v.fetch(context.WithoutCancel(ctx))` (время уже ограничено
`HTTP.Timeout` 4 с). Либо не взводить `failedAt`, когда `ctx.Err() != nil`. Тест: `Verify` с контекстом, который
истекает раньше ответа ключей, затем обычный `Verify` — без ошибки.

**Вердикт: клинап** — одна строка и тест, вход Google — главный путь Блока 4.

### Н-2 · средняя · Удаление аккаунта берёт блокировки не в том порядке, что «по коду» и «Создать семью»

`internal/repository/account_repo.go:36-40, 87` против `household_repo.go:266-293, 313` и `:80`. Здесь два случая.
(а) **Взаимная блокировка** (хвост критика §4, судьба — это ревью). Партнёр вводит код: держит приглашение, ждёт
семью. Создатель кода в ту же секунду удаляет аккаунт: держит семью, ждёт приглашение (`DELETE household_invites
WHERE created_by`). Postgres снимает одну транзакцию — 500, данные целы, повтор проходит. (б) **«Создать семью» во
время удаления** (замечание приёмки): `CreateHousehold` держит строку пользователя и вставляет семью, а удаление этой
строки не ждёт. Его `DELETE app.users` падает на RESTRICT `households.created_by` — 500, у пользователя остаётся
новая семья. Оба случая — две вкладки или два человека в одну секунду. Редко, но это ручка «удалить мои данные».

**Рекомендация.** Один порядок для всех трёх транзакций: **пользователь → приглашения → семьи**. В начале
`DeleteAccount` добавить `SELECT id FROM app.users WHERE id = $1 FOR UPDATE`, затем
`SELECT code FROM app.household_invites WHERE created_by = $1 FOR UPDATE`, и только потом семьи (как сейчас).
`JoinHousehold` (приглашение → семья → вступающий, он не удаляемый) с этим порядком не образует цикла.
`CreateHousehold` будет ждать удаления на строке пользователя, а после него получит «нет пользователя» (тот всё
равно удалён, 401 следующим запросом). Правка в одном файле, `JoinHousehold` не трогается. Это проще варианта из
хвоста («сначала семья, потом приглашение» в `JoinHousehold` с перечитыванием приглашения). Тест: PG «удаление и
`CreateHousehold` одновременно» по образцу `TestPostgresDeleteAccountConcurrent`. Удаление проходит без ошибки,
семьи с `created_by` удалённого нет. Взаимную блокировку тестом не ловим (недетерминирована) — в комментарии
указать порядок.

**Вердикт: клинап** — закрывает хвост §4 «Взаимная блокировка `JoinHousehold`/`DeleteAccount`».

### Н-3 · средняя · Сервер впускает по второму коду третьего полноправного участника

`internal/repository/household_repo.go:325-345` (выбор слота). Хвост §4 «Пригласить партнёра… второй код впускает
третьего», рекомендация критика — сюда («ревью backend Б4»). Клиент прячет код при двух участниках, сервер не
ограничивает: код, выданный раньше (или ручкой), даёт `member` на слоте `c`. После В-1 у слота `c` есть и законная
роль: новый партнёр после ухода прежнего. Поэтому потолок — не «слотов ≤ 2», а «**живых `member` ≤ 2**». Клинап
(Р-124) возвращает «Пригласить» после ухода партнёра — без потолка на сервере третий может войти, пока у обоих
открыт старый код.

**Рекомендация.** В `JoinHousehold` под той же блокировкой семьи:
`SELECT count(*) FROM app.household_members WHERE household_id = $1 AND role = 'member'` ≥ 2 → `ErrHouseholdFull`
(400 `household has maximum members`, тот же ответ). Мок — так же. Тесты: моки + PG «двое → третий по коду — 400»
и «двое → один ушёл → новый по коду — `c`». Viewer по коду не создаётся (только SQL), потолок его не касается.

**Вердикт: клинап** — закрывает хвост §4 (строка «Пригласить партнёра… второй код»), связан с Р-124 того же клинапа.

### Н-4 · низкая · Имя участника: в «по коду» не обрезается, длина нигде не ограничена

`handlers/household.go:60, 157, 178`, `handlers/auth.go:196-198`. `CreateHousehold` обрезает `display_name` и требует
его, тело — до 16 КБ. `JoinHousehold` передаёт имя как есть (пустое → «Участник» в репозитории), тело — до 1 МБ
(старый лимит). Имя из токена Google (`LinkGoogle`, `CreateGoogle`) длину тоже не проверяет. Строка в 1 МБ ляжет в
`household_members.display_name` и уйдёт всей семье в `GET /household/members`. Приёмка отметила «длина не
ограничена».

**Рекомендация.** Один помощник в `handlers/household.go`, например `cleanName(s string) string`: обрезать пробелы и
оставить ≤ 60 рун. Применить в `CreateHousehold` и `JoinHousehold`; лимит тела `JoinHousehold` — `16<<10`, как у
соседей. Имя из Google резать там же, где читаем (`googleauth.Verify`, `Name`). Тест: длинное имя — обрезано.

**Вердикт: клинап.**

### Н-7 · низкая · `POST /api/events`: мусор после JSON, `at` до 30 дней назад

`handlers/events.go:51, 66`. Один `Decode` не замечает хвост после объекта. `at` в прошлом до 30 дней даёт свой
клиент до 30 `app_open` за раз (по одному на день — уникальный индекс).

**Вердикт: не делаем.** Хвост после JSON не проверяет ни одна ручка репо (`decodeJSONBody` — та же конвенция).
Свой клиент шлёт честное время из очереди. Завысить «активных» может только сам пользователь своими запросами —
на 5–10 семьях владелец это увидит. Короткий `eventPast` ломал бы законную очередь телефона, который долго был без
сети.
