## Находки

### Н-1 · средняя · `sanitize` не вырезает управляющие символы — NUL доходит до сервера и ломает сравнение продавцов

`frontend/src/lib/statements/model.ts:27-30`. `\s+` не покрывает `\p{Cc}` кроме пробельных: NUL и
прочие управляющие символы, которые pdf.js отдаёт на неизвестных глифах, остаются в `merchant`,
`counterparty`, `note`. Последствия: (1) после клинапа Н-1 backend такой батч получит 400 навсегда —
голова очереди застрянет и заблокирует все следующие загрузки (хвост §4 → B2C-21); сейчас — 500 на
PG; (2) `normalizeMerchant` отдаёт `magnum\u0000` — словарь и правило семьи не срабатывают, продавец
уходит в «незнакомое». Проверено временным тестом (выше).

**Рекомендация.** Первой операцией `sanitize` удалить управляющие символы:
`text.replace(/\p{Cc}/gu, (c) => (/\s/.test(c) ? ' ' : ''))` — `\t\n\r` становятся пробелом, остальное
**удаляется, а не заменяется пробелом**: номер карты или IBAN, разорванный NUL, склеится и уйдёт
следующими заменами (Р-23 важнее, чем раздельные слова в названии). Тест в `model.test.ts`: NUL и
`\u0001` в названии → их нет, `normalizeMerchant('MAGNUM\u0000 ALMATY') === 'magnum'`,
`'12345\u00006789'` → цифр не остаётся. **Делать до прод-деплоя**: `fingerprint` берёт
`normalizeMerchant`, после деплоя смена `sanitize` дала бы таким операциям новые id (дубли у
повторной загрузки); сейчас на проде операций нет — смена бесплатна.

**Вердикт: клинап** (в паре с Н-1 `REVIEW-backend.md`).

### Н-2 · средняя · две пересекающиеся выписки одного банка в одном выборе задваивают деньги в предпросмотре

`frontend/src/stores/operations.ts:169-173` (черновик), `:247-253` (очередь). Выбор файлов —
`multiple`; «август» и «август–сентябрь» Kaspi дают общие операции с **одинаковыми** id (отпечаток
по строке, ordinal внутри файла). `draftOps` склеивает операции файлов без учёта id, поэтому сводка
(«Операций», «Списания», «Поступления», «Между своими») и суммы вопросов о незнакомом
(`unknownGroups`) считают общие операции дважды — на экране неверные деньги. Очередь: каждый файл
шлёт все свои операции — общие уходят дважды (двойной трафик; сервер схлопывает, вреда данным
нет). Итоги в документе и локальная копия верны — они по id. Проверено временным тестом (выше).

**Рекомендация.** В `draftOps` оставить первую операцию каждого id (`new Map(raw.map((o) => [o.id,
o]))` с сохранением порядка, первое вхождение побеждает). В `send` раздавать id по задачам очереди
один раз (множество уже назначенных): операция уходит с первой загрузкой, в которой встретилась;
`ops_count` записи загрузки — как сейчас, число операций файла. Тест в `operations.test.ts`: два
одинаковых файла → сводка как у одного, `server.batches` — `[60]` + пустой второй батч не
отправляется (задача без операций — только запись загрузки).

**Вердикт: клинап.**
