## Проверено независимо (не по Handoff-у)

- **Разбор JSON в Go 1.27** (скрипт в scratchpad): битый UTF-8 (`\xff`) и одиночный суррогат
  (`\ud800`) `json.Unmarshal` молча заменяет на U+FFFD — `utf8.ValidString` после него всегда
  `true`; `\u0000` проходит как есть.
- **Клиент управляющие символы не чистит:** в `frontend/src/lib/statements/*.ts` нет вырезания
  `\u0000`/`\p{Cc}` (grep).
- **Пулер:** `lib/pq` в режиме `binary_parameters=yes` шлёт `[]byte` бинарно — в
  `statement_repo.go` `[]byte` нет (строки, `*string`, `int64`, `bool`, `time.Time`); CI гоняет PG
  в обоих DSN — зелёный.
- **Конвенция индексов:** в `000001` у внешних ключей, не покрытых PK, индексы есть
  (`household_members_user_idx`, `household_invites_household_idx`); в `000002` — нет (Н-2).
- **Размер кусков:** `upsertChunk = 500` (`statement_repo.go:94`) и `BATCH_SIZE = 500`
  (`frontend/src/stores/operations.ts:28`) — на проде цикл по кускам всегда делает один проход.
- **Логи:** `middleware.Logger` пишет метод, путь и query (`since`, `limit`) — тел нет; хендлеры
  выписок ошибок не логируют вовсе.
- **Схема `app`:** RLS/GRANT нет, как и в `000001` (схема не отдаётся PostgREST); проверка
  безопасности базы — B2C-26.
- **Мок против pg:** `lastByID`, `upload_id` чужой → NULL и `COALESCE` с прежним, общий
  `updated_at` батча, страница не рвётся внутри метки, `ListUploads` новые сверху со слотом —
  совпадают. Роли: viewer — только `GET /api/statements`, остальное 403 (e2e и хендлер-тесты).

## Находки

### Н-1 · средняя · `\u0000` в тексте операции даёт 500 вместо 400; проверка UTF-8 — мёртвая ветка

`backend/internal/handlers/statements.go:170-179`, `:165`. Гвард проверяет длину, 6+ цифр и
`utf8.ValidString`, но Postgres `text` не хранит NUL (`22021 invalid byte sequence … 0x00`) —
батч с `\u0000` в `merchant`/`counterparty`/`note`/`category_id` падает в 500 (тот же механизм,
что уже пойман ревью MGV на реальном PG в синке — строка §4 → B2C-26). pdf.js на неизвестных
глифах отдаёт такие символы, клиент их не вырезает — одна «кривая» выписка = батч, который
не пройдёт никогда (очередь застревает — хвост §4 → B2C-21), и в логах пусто (Н-4).
`utf8.ValidString` при этом недостижим: `json.Unmarshal` уже заменил битый UTF-8 на U+FFFD
(проверено скриптом); `category_id` вообще не проверяется на текст.

**Рекомендация.** В `validateOperation` заменить ветку `!utf8.ValidString(s)` на
`strings.ContainsRune(s, 0)` → `"text field contains NUL"` и прогнать через тот же цикл
`category_id`. Хендлер-тест: `\u0000` в `merchant` и в `category_id` → 400. Клиентская половина
(вырезать `\p{Cc}` в `sanitize`) — в `REVIEW-frontend.md`.

**Вердикт: клинап**

### Н-2 · средняя · у внешних ключей `000002` нет индексов, вопреки конвенции `000001`

`backend/migrations/000002_statements.sql:10` (`statement_uploads.user_id`), `:24`
(`operations.household_id`), `:25` (`operations.upload_id`, `ON DELETE SET NULL`). PK
`(user_id, id)` покрывает только `operations.user_id`. Удаление аккаунта (B2C-24) каскадом
удаляет загрузки пользователя — полным сканом `statement_uploads`, а на **каждую** удалённую
загрузку Postgres выполняет `SET NULL` в `operations` по `upload_id` — полным сканом таблицы
операций всех пользователей. При сотнях загрузок и сотнях тысяч строк — секунды внутри
функции Vercel. Советник Supabase («unindexed foreign keys») отметит все три после применения.
Миграция в прод ещё не применялась (это шаг клинапа) — дополнить её сейчас бесплатно; после —
только новой миграцией.

**Рекомендация.** В `000002` добавить
`statement_uploads_user_idx (user_id)`, `operations_household_idx (household_id)`,
`operations_upload_idx (upload_id)` (`CREATE INDEX IF NOT EXISTS`, как соседние). Локальная
`ffdev` уже с `000002` без них — одноразовая, пересоздать или не трогать. Проверка:
`TestPostgresStatementsMigrationRerun` + запрос к `pg_indexes` в PG-тесте.

**Вердикт: клинап** (до `cmd/migrate` в прод, тем же клинапом)

### Н-3 · средняя · запись нескольких кусков в одной транзакции не покрыта тестом

`backend/internal/repository/statement_repo.go:94,111-152`. Инвариант курсора «строки батча
делят один `updated_at`» держится на том, что все куски по 500 идут в одной транзакции (`now()`
= начало транзакции). Клиент шлёт ровно 500 (`operations.ts:28`), PG-тесты — единицы строк:
ветка `start > 0` (сдвиг номеров параметров `p(i)` от `len(args)`, склейка `RowsAffected`) не
исполнялась нигде, включая стенд. Ошибка в нумерации всплывёт в первый день, когда клиент или
будущая ручка пришлёт больше 500.

**Рекомендация.** PG-тест `TestPostgresStatementsMultiChunkBatch`: 1201 операция (три куска) с
дублем id по разные стороны границы куска → `n == 1200`, в базе 1200 строк, у всех один
`updated_at`, дубль — поздняя версия; тот же тест с `ListOperations(limit=1)` отдаёт все 1200
одной страницей.

**Вердикт: клинап**

### Н-4 · низкая · ошибки репозитория в ручках выписок не пишутся в лог

`backend/internal/handlers/statements.go:124-126, 137-140, 205-208, 239-242`. 500 уходит клиенту
без следа в логах Vercel. Так же молчит `sync.go`, но `auth.go:88` и `fx.go:25` пишут — конвенции
нет; для выписок цена выше: первая настоящая загрузка на проде (смоук клинапа) идёт через пулер,
и при сбое понять причину будет нечем. Тела операций в лог не попадут: `lib/pq` `Error()` — это
`Message` без `Detail` («Failing row contains …» сидит в `Detail`), а значения, которые Postgres
цитирует в `Message` (дата, uuid), хендлер к этому моменту уже проверил.

**Рекомендация.** `log.Printf("statements: <ручка>: %v", err)` в четырёх ветках 500 — только
ошибка, без полей запроса.

**Вердикт: клинап**

### Н-5 · низкая · число операций и загрузок у пользователя не ограничено

`backend/internal/handlers/statements.go:186-211`, `:101-129`. Ограничены батч (2000 строк /
2 МБ) и страница, но не объём: member может слать батчи с новыми id без конца и забить базу
Supabase (общий лимит проекта). Для своей семьи — неважно; для чужих людей B2C (Блок 4) — да.
Документы синка ограничены по природе (одна строка на семью/человека), операции — нет.

**Рекомендация.** В B2C-26 («безопасность базы»): потолок строк `operations` на пользователя
(проверка счётчиком в транзакции upsert, 413/409) и загрузок в сутки.

**Вердикт: хвост §4** → Блок 4, B2C-26 (судьбу — владельцу)

### Н-6 · низкая · хелперы `errorJSON`/`caller`/`member` есть только в `statements.go`

**Вердикт: не делаем** — переписывание рабочих хендлеров ради единообразия — попутная

### Н-7 · низкая · гвард цифр не видит номер с пробелами и не-ASCII цифры

`backend/internal/handlers/statements.go:49`, CHECK `000002:30-32`. `[0-9]{6,}` пропускает
«4400 4301 2345 6789» и полноширинные `１２３４５６`.

**Вердикт: не делаем** — Р-23 сформулировано как «6+ цифр подряд», сервер — вторая линия;
в корпусе номера карт маскированы, ИИН идёт сплошной строкой. Расширять — решением к Р-23, не
ревью.
