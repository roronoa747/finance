## 1. Цель

Превратить Family Finance из инструмента одной семьи в B2C-продукт для пар и одиночек
Казахстана: главный экран продаёт мечту (цель с фото и «до мечты N%»), а ритм держит
еженедельная выписка банка, разобранная прямо на телефоне; тот же код доводится до сайта,
Google Play и App Store. Успех: незнакомые семьи загружают вторую выписку в течение 14 дней и
возвращаются каждую неделю; данные прода не потеряны ни одним деплоем; выписка не покидает
телефон.

Режим процесса: **M**; блоки 1, 3, 4, 6, 8 — **L** (пометки в §4). Блок 2 — без кода
(отклонение — §5). Деплой веб-версии после каждого блока с кодом; магазины — релизы Блоков 7 и 8.

## 2. Зафиксированные решения

Р-1…Р-20 — из резюме бриф-интервью (источники там же); Р-21…Р-30 — развилки, которые бриф
отдал составителю (технические дефолты, подтверждены вместе с резюме 2026-09-26).

- **Р-1. Граница инициативы — до App Store включительно.** Один бэклог: веб-проверка гипотезы
  (сайт) → Android → iOS. *(владелец, раунд 1)*
- **Р-2. Один общий план вместо трёх бэклогов.** `развитие-приложения` закрыт (Блоки 0–2 🏁;
  Блоки 3–7 переосмыслены: RP-14…17 «желания и цели с фото» → Блок 3 здесь; RP-19 «поделиться →
  в приложение» → «поделиться выпиской» в Блоке 7; RP-18, RP-20…28 — после магазинов).
  `паритет-react-vue` закрыт (все блоки 🏁). Хвосты обоих — в §4 с судьбами (Р-30).
  `credits-flow` (бриф без бэклога, поглощён Блоком 1 RP) — в архиве. Выполнено составителем
  2026-09-26 (Блок 0). *(владелец, раунды 2–3)*
- **Р-3. Порядок блоков:** парсер → дизайн → экраны и флоу → фундамент для чужих → недельный
  ритм → ИИ по выбору (условный, после замера) → Android → iOS. *(владелец, раунд 2)*
- **Р-4. Выписка разбирается на телефоне** (PDF — pdf.js в браузере; Excel — если такой формат
  окажется в корпусе); файл на сервер не уходит и нигде не хранится. Банки на старте — **Kaspi и
  Freedom** (корпус владельца есть); Halyk и BCC — когда появятся выписки: у каждого банка свой
  парсер и свой корпус. Корпус лежит вне git (`memory/secrets/statements/`, инвариант 11), тесты —
  на обезличенных копиях, собранных из корпуса (имена, номера, суммы заменены). Первая задача
  парсера — инвентаризация корпуса. *(владелец, раунды 1–2; корпус вне git и фикстуры — дефолт)*
- **Р-5. Данные выписок.** Операции — личные: у каждого участника своё хранилище на сервере (без
  ФИО и номеров счетов: продавец, дата, сумма, категория, банк), партнёру операции не видны. В
  общий документ уходят итоги по категориям за неделю и месяц с суммами — партнёр видит категории
  до тенге. Переводы между партнёрами и между своими счетами и банками — внутренние, в траты не
  входят (сопоставление по сумме и дате); переводы людям — своя категория с памятью «кому → что».
  Повторная загрузка того же периода не удваивает операции (отпечаток операции). *(владелец,
  раунд 1; внутренние переводы и отпечаток — дефолт)*
- **Р-6. Выписка предлагает сопоставление с отметками по одному решению:** «похоже, это платёж по
  Автокредиту — отметить?», «это зарплата Ильяса?»; «да» запоминается по продавцу и назначению, и
  дальше такие строки отмечаются сами (снять можно); ручные «Оплатил» и «Пришла зарплата»
  остаются. Модель записей `payments` не меняется — сопоставление ставит ту же запись с пометкой
  источника «выписка». *(владелец, раунд 1; модель записи — дефолт)*
- **Р-7. Первый запуск — из выписки, мастер настройки исчезает.** Google → «с кем» (один / создать
  семью / по коду) → загрузить выписку → приложение находит зарплату и повторяющиеся платежи и
  спрашивает по одному («это ваш доход?», «это аренда / кредит / подписка?») → картина недели →
  «на что копим» (цель со сроком). Ручной ввод дохода, обязательств и кредитов остаётся вторым
  уровнем. Один человек — тоже семья, партнёр опционален. *(владелец, раунд 4 и пивот;
  одиночка — дефолт)*
- **Р-8. Главный экран — «До мечты: N%».** Главная цель с фото — герой; под ней картина недели по
  категориям, «Свободно до конца месяца» по факту выписок обоих и ближайшее решение недели.
  *(владелец, раунд 2; состав под героем — дефолт)*
- **Р-9. Цели с фото и шаблоны.** Фото цели и желания — в своей таблице Postgres через Go-ручку
  загрузки, сжатие на телефоне (порядка 100 КБ, webp) — как Р-8 RP. Сборник шаблонов: пять типов
  из брифа (машина, квартира, путешествие, техника, здоровье) и популярные направления с
  отобранными картинками (Unsplash с указанием автора) либо своё фото; без советов, чек-листов и
  цен. Списки желаний по людям и скрытые подарки в `private_docs` — как Р-9/Р-10 RP, по ходу
  дизайна. *(владелец, раунд 3; хранилище — Р-8 RP)*
- **Р-10. Социальное наружу — карточка для сторис без сумм** («накопили 60% на Японию»,
  «отказались от 3 подписок»): картинка с фото цели и процентом через системное «Поделиться».
  Друзья, реакции, лента — после магазинов. Внутри пары — без сравнений участников (Р-22 RP).
  *(владелец, раунд 3)*
- **Р-11. Дизайн делает агент:** референсы (Mobbin через подключение, если работает без оплаты;
  иначе публичные скриншоты приложений из списка брифа) → мудборд → 5–7 ключевых экранов и
  лэндинг в Figma через подключение → владелец утверждает → перенос в код на токенах
  `frontend/src/style.css` и ките. **Тон — тёплый и образный, но взрослый:** фото мечты и крупная
  типографика, спокойные цвета, мало кнопок; без конфетти, значков, серий и маскотов (Р-21 RP
  сохраняется); запрет на ИИ-слоп остаётся. Основа — iPhone; тёмная тема обязательна.
  *(владелец, раунды 1 и 3; Mobbin — дефолт)*
- **Р-12. ИИ — по выбору пользователя.** Обещание «без ИИ» снято: позиция «можно с ИИ, можно
  без». До магазинов — только категории незнакомых названий продавцов: сначала замер на корпусе,
  какую долю строк словарь и память не узнают; если заметную (Р-29) — кнопка «спросить ИИ» (уходит
  только название, без сумм и ФИО), Gemini через Go по образцу Р-17/Р-26/Р-28 RP, честный экран
  «что уйдёт в Google». ИИ-разбор бюджета и скриншотов — после магазинов. *(владелец, раунды
  1, 3, 4)*
- **Р-13. Вход — Google OAuth** (ID-токен Google → проверка в Go → свой JWT, как сейчас); почта и
  пароль убираются с экрана (ручки Go остаются для локального стенда и e2e — дефолт); существующие
  пользователи привязываются по email. Пользователь без семьи допустим: после входа — шаг
  «с кем»; «по коду» без своей семьи работает — закрывает хвост «новые семьи» `STATE.md`.
  Sign in with Apple — в блоке iOS (обязателен при входе через Google). *(пивот; детали — дефолт)*
- **Р-14. До публичного запуска обязательно:** удаление аккаунта вместе с данными, политика
  конфиденциальности на домене, проверка безопасности базы (PostgREST не отдаёт схему `app`;
  старые таблицы `public` и ключи React — в «Уборку старого»), лэндинг с демо и «начать» →
  Google; домен покупается в начале инициативы. *(бриф; домен — владелец, раунд 1)*
- **Р-15. Недельный ритм — Web Push обоим.** Подписка на пуш в приложении (VAPID, подписки в
  Postgres), рассылка из Go по расписанию Vercel cron; по умолчанию воскресенье вечером по
  Алматы, день и час настраиваются. Партнёр не загрузил — картина недели с пометкой «без выписки
  <имя>» и повторный пуш ему; ничего не блокируется. iPhone получает пуш только установленным на
  «Домой»; в оболочках магазинов — нативный пуш. *(владелец, раунд 4)*
- **Р-16. Метрика удержания — свои события в Postgres:** «вторая выписка в течение 14 дней»
  считается из записей загрузок; минимальные события (открыл, завершил неделю, дошёл до цели в
  первом запуске) без третьих сторон; страница цифр для владельца. *(владелец, раунд 4)*
- **Р-17. Бесплатно до проверки удержания:** без платной стены и покупок в магазинах;
  монетизация — отдельный бриф после данных. *(владелец, раунд 2)*
- **Р-18. Магазины — Capacitor поверх того же кода** (не Flutter): Android первым, iOS — на Mac
  владельца. Аккаунты Google Play (25 $ разово), Apple Developer (99 $/год) и домен приняты как
  исключение из правила бесплатных тарифов. «Поделиться выпиской из банка → в приложение» —
  через share target оболочки. Сборка со встроенными файлами, релиз через магазин;
  live-обновления — после. *(владелец, раунд 1 и пивот; сборка — дефолт)*
- **Р-19. Инварианты остаются:** деньги — целые тенге, считает `finance.ts`; цвет — только
  токены; документ и слияние (Р-7/Р-14 RP), новые данные — записи с id; миграции только
  добавляют; деплой после каждого блока, откат — promote; данные прода не теряются ни одним
  деплоем. *(дефолт)*
- **Р-20. Аудитория:** Казахстан, русский интерфейс, тенге; пары и одиночки. *(дефолт из выбора
  банков)*
- **Р-21. Хранилище операций — таблицы, не документ.** `app.statement_uploads` (запись о каждой
  загрузке: кто, банк, период, сколько операций — видна семье) и `app.operations` (личные, PK
  `(user_id, id)`, `id` — отпечаток операции; клиент забирает по курсору `updated_at`). Итоги по
  категориям — записи `SyncDoc.spendTotals` (id = `участник:вид:период:категория`, LWW по id) —
  их считает телефон загрузившего из всех его операций периода и пишет в общий документ.
  *(дефолт составителя — развилка брифа)*
- **Р-22. Словарь и память.** Разделы трат — список `SyncDoc.spendCategories` (сеется дефолтным
  набором при первой загрузке, семья правит названия и цвета, хардкода справочника в экранах
  нет). Стартовый словарь «слово в названии → раздел» — данные в коде (`lib/statements/
  dictionary.ts`). Память семьи «продавец → раздел» и «кому → что» — записи `merchantRules` в
  **личном** документе (переводы людям не утекают партнёру), поэтому слияние личного документа
  (бывший RP-15) входит в Блок 1. *(дефолт составителя — развилка брифа)*
- **Р-23. Парсер — две ступени:** файл → строки (pdf.js ленивым чанком; xlsx — по корпусу) →
  операции (чистые функции, свои у каждого банка). Фикстуры тестов — обезличенные строки, снятые
  с корпуса скриптом. В результате парсера нет последовательностей из 6 и более цифр (номера
  карт, счетов, ИИН) и полных ФИО — имена остаются такими, как печатает банк (имя и инициал).
  *(дефолт составителя)*
- **Р-24. Идентификаторы и ветки.** ID задач — `B2C-NN`; ветки — `b2c-block-N-<тема>` от `main`.
  Merge в `main` + push = прод-деплой (Vercel Production из `origin/main`) — только в деплоящей
  роли и с «да» владельца в той сессии; push ветки блока ради CI — с согласия. *(дефолт)*
- **Р-25. Google на сервере и в оболочках.** Go проверяет ID-токен Google по JWKS Google (RS256
  через уже подключённый `golang-jwt`), допустимые аудитории — `GOOGLE_CLIENT_IDS` (веб, Android,
  iOS через запятую). В веб — Google Identity Services; в оболочках Capacitor — нативный плагин
  входа Google (WebView не допускает OAuth Google), тот же ID-токен на ту же ручку. Пользователь без
  семьи получает JWT без `household_id`; ручки семьи отвечают ему 409 `no household`.
  *(дефолт составителя)*
- **Р-26. Push.** Веб — Web Push (VAPID, библиотека `webpush-go`); оболочки — FCM (Android, а iOS
  через APNs средствами Firebase). Одна таблица `app.push_subscriptions` с видом `web` / `fcm`;
  день и час напоминания — поля семьи. Рассылка — расписание **GitHub Actions cron ежечасно**
  (как «будильник» базы `.github/workflows/keep-supabase-awake.yml`; Vercel Cron на бесплатном
  тарифе бежит раз в сутки — не подходит для настраиваемого часа) → `GET /api/cron/weekly` с
  заголовком `Authorization: Bearer <CRON_SECRET>` (секрет — в env Vercel и в Secrets GitHub).
  *(дефолт составителя)*
- **Р-27. События метрики** — таблица `app.events` (`kind`, `at`, пользователь, семья; без
  свободного текста); страница `/admin` только владельцу — email из `ADMIN_EMAILS` (env). *(дефолт
  составителя)*
- **Р-28. Шаблоны целей.** Картинки Unsplash в сборку не встраиваются: список шаблонов (тип,
  название, id фото, автор, ссылка) — данные в коде; при выборе шаблона картинка скачивается на
  телефон, сжимается и загружается как своё фото цели (автор сохраняется в цели и показывается);
  офлайн шаблон выбирается без картинки. *(дефолт составителя)*
- **Р-29. Порог для Блока 6:** доля незнакомых названий «заметная», если после словаря и памяти не
  узнано более 15 % строк трат или более 25 % суммы трат месяца на корпусе владельца (среднее по
  месяцам). Ниже порога — Блок 6 отменяется записью в §4. *(дефолт составителя; владелец правит)*
- **Р-30. Судьбы хвостов RP и PV** проставлены составителем по рекомендациям критиков и приняты
  владельцем пакетом 2026-09-26 (таблица §4). *(владелец, сессия `/backlog`)*

## 6. Технический контекст

Факты, нужные двум и более задачам. Факт одной задачи — в её ТЗ. Актуально на 2026-09-26
(после Блока 2 RP и Блока 5 PV); критик каждого блока дописывает сюда строку «после Блока N».

**Где что лежит**
- Прод: `family-finance-ff.vercel.app` (домен — B2C-26), Vercel, регион функций `icn1`
  (`vercel.json`: `installCommand`/`buildCommand` с `--prefix frontend`, `outputDirectory`
  `frontend/dist`, `/api/(.*)` → `/api/index`, остальное → `index.html`). Go — одна функция
  `api/index.go` (корневой модуль `finance-vercel`, `replace finance-backend => ./backend`; новая
  зависимость бэкенда — и в корневой `go.mod`/`go.sum`). Vue — `frontend/`.
- Бэкенд `backend/`: `server/server.go` — `NewHandler(cfg, db)` (nil db → моки, прод отказывает),
  `FromEnv()` (функция Vercel, всегда прод-проверки), `NewRouter(cfg, db, repos, tokens, fxClient)`
  — все маршруты под `/api`; защищённая группа `auth.Middleware(tokenService)`; роль проверяется в
  хендлере (`auth.GetUserID/GetHouseholdID/GetRole/GetSlot`, `internal/auth/middleware.go`).
  Хендлеры `internal/handlers/*.go` (`decodeJSONBody(w, r, limit, dst)` → 413/400, `respondJSON`);
  репозитории `internal/repository` — интерфейсы `UserRepository`, `HouseholdRepository`
  (`GetMembers` есть, ручки нет), `DocRepository`; pg-реализации `NewSQL*Repository(*sql.DB)`,
  моки `mock_repo.go` (`NewMockRepositories()`); `server.Repos{Users, Households, Docs}` — новый
  репозиторий добавляется сюда, в pg и в мок. Конфиг `internal/config/config.go`: `getEnv`,
  `ValidateProduction()` (обязательны `DATABASE_URL`, `JWT_SECRET` ≥ 32); новые переменные —
  опциональные, с честным выключением функции без них. Образец внешнего HTTP — `internal/fx/fx.go`
  (`Client{HTTP, BaseURL, TTL, Now}`, таймауты, `io.LimitReader`, тесты `httptest`).
- БД: Supabase Postgres, схема `app` (`backend/migrations/000001_init.sql`: `users` (`email`
  UNIQUE, `password_hash` NOT NULL — B2C-22 снимает NOT NULL), `households`, `household_members`
  (`slot` a/b/c, `role` member/viewer), `household_docs`, `private_docs`, `household_invites`).
  Миграции встроены `//go:embed *.sql`, каждая в своей транзакции; `cmd/server` применяет на
  старте, функция Vercel — никогда; в прод — `cmd/migrate` вручную (5432). Все имена в SQL
  квалифицированы `app.`. Функция ходит через пулер 6543 с `binary_parameters=yes` — JSON в SQL
  передавать строкой, не `[]byte`. Строки подключения — `memory/secrets/supabase-db.md`.
- JWT HS256 (`internal/auth/jwt.go`): `user_id`, `household_id`, `role`, `slot`, TTL 30 дней.
  Фронт: токен — `localStorage['ff_auth_token']`, `Authorization: Bearer` (`api/client.ts`,
  класс `ApiClient` с `request<T>`, `ApiError(status)`, `isConflict`); `<img src="/api/...">`
  токен не несёт. `stores/auth.ts`: `setAuthData`, `clearAuth`, `isDemo` (`DEMO_TOKEN`),
  `ff_user`/`ff_household`/`ff_member` в `localStorage`.
- React в корневом `src/` — не трогать (уборка — хвост `STATE.md`).

**Документ и слияние (сердце всех блоков)**
- Типы — `frontend/src/types/finance.ts` (`SyncDoc`: `people`, `categories`, `goals`, `wishlist`,
  `obligations`, `accounts`, `credits`, `payments?`, `plans?`, `setupDoneAt?`, `resetAt?`;
  `Tracked = { updatedAt, deletedAt? }`, `PersonId = 'a' | 'b' | 'c'`). Слияние —
  `frontend/src/lib/merge.ts` `mergeDocs(local, remote)`: объект `known` перечисляет ключи и способ
  слияния; описательные поля — LWW по `updatedAt`, надгробие `deletedAt` сильнее правки и не
  воскресает; append-only списки — объединение по id; `mergeList` берёт `{ ...проигравший,
  ...победитель }` → поле очищать `null`; незнакомые ключи верхнего уровня не теряются
  (`mergeUnknownKeys`); `resetAt` — документ с поздней меткой целиком; `isEmptyDoc`.
- **Правило для новых данных (Р-19):** всё, что может прийти с двух устройств офлайн, — записи с
  id в отдельном списке верхнего уровня; остатки выводятся из записей. Новый список: тип `SyncDoc`
  → `defaultSyncDoc()` (`stores/finance.ts`) → **явно** в `known` `mergeDocs` (`mergeList` по id).
  Старые документы приходят без ключа — читать `doc.x ?? []`. Повтор «снять → отметить снова» —
  новая запись с новым id.
- Стор `frontend/src/stores/finance.ts`: `mutateHouseholdDoc(fn)` / `mutatePrivateDoc(fn)` —
  единственный путь правки (`dirty`, `localStorage`, `scheduleSync`); `syncHousehold` (GET →
  `mergeDocs` → push, до 4 попыток на 409, `unsent`, `forceReplace`), `pullHousehold`,
  `pullPrivateDoc` (сервер поверх локального), `pushPrivateDoc` (без слияния, 409 → ошибка — до
  B2C-05); `privateDoc` — `Record<string, unknown>` (сейчас `accounts`); геттеры `credits` /
  `accounts` / `householdAccounts` — производные остатки (никогда не звать `creditBalance` /
  `accountBalance` на их результате); демо (`isDemo`) — без запросов. Движок
  `stores/syncEngine.ts`: `startSyncEngine` — `online`, `focus`, `visibilitychange`, интервал
  `BACKGROUND_SYNC_MS` 60 с; первый круг — полный синк (хвост → B2C-25).
- Сервер хранит `data` как есть (`handlers/sync.go`, `repository/doc_repo.go`): `POST
  /api/sync/household` — только `member` (403), тело ≤ 10 МБ, невалидный UTF-8 → 400; конфликт
  ревизий → 409 с `server_doc`; успешный push сохраняет ключи верхнего уровня, которых нет в
  присланном (`data || pushed`). Личный документ — `GET/POST /api/sync/private`, тот же протокол.
- Записи `SyncDoc.payments`: `kind` `obligation` / `credit` / `prepay` / `salary`, `targetId`,
