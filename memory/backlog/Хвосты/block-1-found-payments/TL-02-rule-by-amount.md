# TL-02 — Правило платежа по продавцу и сумме (фронт)

Блок 1 · MVP · Репо/каталог: `frontend/` · Зависит от: TL-01 · Роли: member · Х-7, Р-2

## Контекст (что уже есть)

  PaymentRule` :95). `lib/statements/model.ts:177` `ruleFor(op, rules)` — сначала получатель, потом продавец; **побеждает
  последнее живое правило** этого ключа. `fromRule` :164-174 — раздел из правила платежа; операция, что не подходит
  (`fits`), получает `restCategoryId`.
- «В платежи» → `stores/operations.ts:708` `addToPayments(opId, obligationId)`: `markPaid('obligation', …, {period:
  nearestPeriod(op.date, o.day), amount, source: 'statement', opId, at})` (если период не оплачен), затем
  `recategorize(ruleMatchOf(op), {payment: {kind: 'obligation', targetId, categoryId: matchCategory('obligation', o)}})` →
  `recategorizeAll` :728 → `answerAll` :420 — **правило на продавца целиком**; второе правило того же продавца заменяет
  первое.
- `lib/statements/firstRun.ts:260` `recurringOf` молчит, если у продавца есть правило `payment` (:266-267) — поэтому вторую
  подписку того же продавца через «В платежи» не завести (только через «Деньги»).
- Сопоставление — `lib/statements/matching.ts`: `AMOUNT_TOLERANCE = 0.02` :37, `ESTIMATE_TOLERANCE = 0.3` :39, `DAY_WINDOW =
  5` :45; `ruleHit(op, payment, targets)` :110 (обязательство — ±2 % `amountAt(o, period)` в месяц, когда платёж положен;
  оценка — без предела; кредит — ±2 % `creditDueAmount` или ровно `c.payment`); `matchCandidates` :219-313 (ярус 0 — правило
  + `ruleHit`, ярус 1 — эвристика; одна операция и одна пара «цель · месяц» — один раз).
- Сумма обязательства — `householdDoc.obligations[].versions[{from, amount}]`, читать через `amountAt` (`lib/finance`).

## Задача

1. **Несколько правил платежа у одного продавца.** «В платежи» по второй подписке продавца добавляет второе правило
   (`to.payment` с другим `targetId`), не затирая первое. Правила по разделу/внутренние/людям — «последнее побеждает», как было.
2. **Выбор платежа по ближайшей сумме.** Если у ключа продавца несколько живых правил `payment`, операция относится к тому,
   чья текущая сумма (`amountAt` на месяц операции; у кредита — `creditDueAmount`/`payment`) ближе к `−op.amount`; при равенстве
   — последнее правило. Одно правило — как сейчас («продавец целиком», Р-2 дефолт). Отметка, раздел (`fromRule`), «Подорожало»
   и сопоставление (`ruleHit`) идут от выбранного правила.
3. **«В платежи» у второй подписки.** `recurringOf` не молчит, если у продавца есть правило `payment`, но в одном месяце окна у
   продавца есть **и списание по уже заведённому платежу (±5 % его суммы), и эта операция вне ±5 %** — это вторая подписка.
   Если в месяце только одна операция продавца и она дороже заведённой суммы — это «подорожало», `recurringOf` молчит, как
   сейчас.
4. `addToPayments` пишет правило с новым `targetId` рядом с существующими (одна точка записи правил — `answerAll`; новой
   абстракции не заводить).

## Тесты

- `src/lib/statements/model.test.ts` (`ruleFor`): два правила `payment` одного продавца, суммы 1 990 и 4 990 → операции 1 990
  и 5 000 уходят каждая к своему; одно правило — всё к нему (старое поведение); правило по разделу у того же продавца —
  «последнее побеждает».
- `src/lib/statements/firstRun.test.ts` (`recurringOf`): продавец с правилом, в месяце 4 990 (заведено) + 1 990 → для 1 990
  предлагает; только 5 900 в месяце (подорожала) → молчит.
- `src/lib/statements/finds.test.ts`: две подписки продавца, подорожала одна → «Подорожало» по ней, вторая не задета.
- `src/stores/operations.test.ts` («В платежи» addToPayments :1329): вторая подписка → два правила, обе операции отмечены,
  в «траты» не уходят (`unmarked` раздела = 0).
- e2e `e2e/tl-block1-found-payments.test.ts`: магазин приложений, две подписки разной суммы → обе заводятся через «В платежи»,
  обе отмечены в следующем месяце.

## Критерии приёмки

- Вторая подписка того же продавца заводится через «В платежи» и отмечается своей суммой; подорожавшая подписка остаётся
  платежом (не трата) и даёт карточку «Подорожало».
- Записанные до блока правила «продавец целиком» работают без миграции.
- `npm run build && npx vitest run` зелёные; стенд: два платежа одного продавца в «Деньгах → Платежи».
