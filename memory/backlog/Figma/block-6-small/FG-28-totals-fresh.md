# FG-28 — Итоги разделов по свежим операциям: второй свой телефон не откатывает `spendTotals` (фронт)

Блок 6 · MVP · Репо/каталог: `frontend/src` · Зависит от: — (Блок 5 на проде) · Роли: участник (свои итоги); viewer не пишет

Тот же класс, что FG-Х7/FG-27, у **итогов разделов**: второй свой телефон со старой копией операций по сигналу документа

## Задача

1. **Итоги по сигналу документа — только по свежей копии.** Путь `byDoc` у `writeTotals` (и `settleReleased(…, byDoc)`) идёт
   целиком тем же порядком, что `spentFresh` (FG-27): демо — сразу по копии; viewer — ничего; удачного `pull` в запуске не было
   или последний не удался — **отложить** (`totalsDue`: множество периодов `kind:period` либо флаг «пересчитать свежие периоды»),
   пишет следующий удачный `pullOnce` там же, где `spentDue`; иначе `pullFresh()` → удачный `pull` → обычный `writeTotals(periods)`
   (его `writeAccountSpent` по уже свежей копии — отдельный `spentFresh` после этого не нужен: одна запись, не две). **Периоды
   считать после `pull`**, не до: копия могла не знать целую неделю (`recentOperations(all.value)` у отметок и целей платежей —
   пересчитать по свежей копии; у правок операций и снятых отметок — список id тот же, строки берутся из свежей копии).
   Один сигнал — один запрос `GET /operations` (каскад наблюдателей ждёт идущий `pulling`, как в FG-27); `spentFresh` остаётся
   частным случаем того же пути (без периодов) — не плодить вторую копию логики.
2. **`pull`, принёсший чужие для копии строки, пересчитывает их периоды.** В `pullOnce` после успеха: строки, которых в копии не
   было (новый id, не из своей очереди `flush`) или которые ушли (`gone`), → `writeTotals(periodsOf(recentOperations(<эти строки>)))`
   прямым путём (копия только что свежая). Так второй свой телефон сам догоняет выписку первого на ближайшем круге движка
   (60 с), а первый — ручную трату второго; и то и другое — без сигнала документа. Ничего не изменилось → `sameTotal` не пишет
   (проверить, что лишних ревизий документа нет); первый `pull` запуска (курсор пуст, все строки «новые») — только свежие периоды
   `recentOperations`, записи равны — не пишутся. `settlePhone` / `stale` — как были (не дублировать их периоды второй раз в
   одном `pullOnce` — объединить в один вызов `writeTotals`).
3. Чистые функции `lib/finance.ts` (`spendTotals`, `spentSince`), `lib/statements/matching.ts`, типы, UI, `merge.ts` — **без
   изменений**; деньги — целые тенге (правило 6). Бэкенд не трогаем.
4. `clear()` сбрасывает `totalsDue` вместе с `spentDue`. JSDoc у `writeTotals` — одна фраза про `byDoc` по новому смыслу.

## Тесты

- `stores/operations.spend.test.ts`, describe «FG-28» (помощники FG-27): (1) «Оплатил» партнёра при старой копии (`local` 2 500,
  сервер ответит ещё 12 500) — до ответа `pull` `spendTotals` **не пишутся** (ни 2 500, ни 0), после — раздел = 15 000, запрос один;
  **тест FG-27 (5)** `:238` переписать под это (строки `:251-252`); (2) `pulledOk === false` → сигнал документа итоги не пишет
  (`totalsDue`), первый удачный `pull` пишет их по пришедшим операциям; ошибка сервера после удачного `pull` — то же (`pullFailed`);
  (3) `pull` без сигнала документа принёс строку выписки этой недели с другого телефона → итоги недели (и `accountSpent`)
  переписаны; повторный `pull` без новых строк → записи документа не меняются (ревизия/`setHouseholdDoc` не зовётся лишний раз);
  (4) демо — итоги сразу без запроса; viewer — ничего (как FG-27 (4)).

  `pull` теряется) → юнит 2 красный.

## Критерии приёмки

- Стенд (Go на моках, Vite; Chrome 390, обе темы; семья из двух, A1/A2 — один вход в двух контекстах, B — отдельный пользователь,
  как в приёмке Блока 5): выписка A1 → «Оплатил» B → круг A2 раньше A1 — итоги разделов недели A на сервере (документ семьи на
  моках) не прыгают 3 круга; «Неделя» у A1, A2 и одна и та же строка раздела; ручная трата на A2 со старой копией → через круг
  движка у A1 и A2 итоги недели и «На карте» сходятся до тенге. Один телефон на человека — регрессия (`fg-block2-*`, `fg-block3-*`,
  `fg-block5-*`).
- `cd frontend && npm run build && npx vitest run` зелёные (весь набор); бэкенд не тронут.

- Окно свежести `PULL_FRESH_MS` от сигнала документа — FG-29 (тот же `pullFresh`; делается следом в этой ветке).
- Серверная ревизия записей итогов / «последний пишущий побеждает» в `merge.ts` — нет (Р-10).
- Привычки и находки (`writeHabitTotals`, `writeReviewFinds`) отдельно не трогаем — они идут внутри `writeTotals` тем же путём.
- UI, `lib/finance.ts`, `matching.ts`, типы — без изменений.
