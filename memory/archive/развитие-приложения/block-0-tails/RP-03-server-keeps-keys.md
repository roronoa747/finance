# RP-03 — Сервер не теряет ключи документа от старого клиента (бэкенд)

Блок 0 · MVP · Каталог: `backend/` · Зависит от: RP-02 · Роли: member

## Контекст (что уже есть)

- Р-14, Р-31: старый клиент (JS до RP-02) при слиянии выбрасывает незнакомые ключи верхнего
  уровня и пушит документ без них. RP-02 чинит это только в новом клиенте; первый запуск
  старого JS после деплоя Блока 1 всё ещё может стереть, например, `payments`.
- `backend/internal/handlers/sync.go` `PushHouseholdDoc` (и `PushPrivateDoc`): тело
  `{last_seen_rev, data}` (`json.RawMessage`), проверка `utf8.Valid`, затем
  `docRepo.PushHouseholdDoc(ctx, householdID, lastSeenRev, data, userID)` → `(doc, conflict,
  err)`; при совпадении ревизии данные пишутся **как есть**. Лимит тела —
  `maxDocBodyBytes = 10<<20`.
- Репозиторий: `internal/repository/doc_repo.go` (pg, JSON передаётся строкой — не `[]byte`,
  из-за `binary_parameters`), `mock_repo.go` (моки). Тесты: `internal/handlers/sync_test.go`,
  `internal/repository/pg_integration_test.go` (`TestPostgres*`), `server/server_e2e_test.go`.
- Новый клиент (после RP-02 и задач блоков) всегда шлёт все ключи, которые знает, — пустые
  списки как `[]` (`defaultSyncDoc()`), так что «ключ отсутствует» = «клиент о нём не знает».
- Сброс данных (`resetDoc` → `forceReplace`) шлёт `defaultSyncDoc()`; ключей, которых не
  знает новый клиент, в проде нет.

## Задача

1. При успешном push (ревизия совпала) ключи **верхнего уровня**, которые есть в хранимом
   документе и **отсутствуют** в присланном `data`, переносятся из хранимого в записываемый
   документ. Ключи, присланные явно (включая `[]` и `null`), не трогаются.
2. Сделать это атомарно с проверкой ревизии (в той же транзакции / том же условном
   `UPDATE`), чтобы между чтением и записью не вклинился другой push. Способ — на выбор
   исполнителя (например, `jsonb` `stored || pushed` в SQL для объектов верхнего уровня);
   записать выбор в Handoff.
3. То же для `private_docs` (тот же риск для личных счетов и будущих скрытых желаний).
4. Моки (`mock_repo.go`) повторяют поведение — хендлер-тесты на моках должны видеть то же.
5. Комментарий у места слияния: зачем (Р-14, старый PWA) и почему только верхний уровень.

## Тесты

- Хендлер/репо на моках: хранимый `{people:[…], payments:[…]}`, push `{people:[…]}` с
  верной ревизией → в ответе и в хранилище `payments` сохранены; push с `payments: []` →
  список пуст (явное значение уважается).
- `TestPostgres…` на реальном Postgres — тот же сценарий + конфликт ревизии (409) не
  меняет хранимое.
- `server_e2e_test.go` не ломается.

## Критерии приёмки

- `cd backend && go build ./... && go vet ./... && go test ./...` зелёные; PG-режим
  (`TEST_DATABASE_URL=… go test -p 1 -count=1 -run Postgres ./...`) зелёный; CI
  `ci-backend` зелёный.
- Регистрация (`{}`) и первый push нового клиента работают как раньше.

## Вне скоупа

- Слияние вложенных полей на сервере (сервер не знает схему документа — это клиент, RP-02).
- Любые другие изменения API синка.
