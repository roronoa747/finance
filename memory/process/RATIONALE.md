# Критический разбор исходного подхода (arealapp) и что изменено в эталоне

Исходник: `arealapp/platform/docs` — BACKLOG-GUIDE, эталонный бэклог zones-kanban
(7 блоков, ZK-01..19), лёгкий utc-admin, каталожные ревью admin-ui-fixes, CHAIN.md
caddy-migration. Разбор сделан 2026-08-01 при извлечении механики в этот фреймворк.

## Что в исходном подходе сильное (сохранено без изменений)

1. **Зафиксированные решения Р-*** — «конституция» бэклога. Главная находка подхода:
   LLM-сессии перестают пересматривать архитектуру, владелец решает один раз.
2. **Контекст-диета** — явный список чтения на сессию. Экономит токены и, важнее,
   убирает шум: сессия не тонет в живых доках и не тащит в решение нерелевантное.
3. **Самодостаточные ТЗ** (Контекст/Задача/Критерии/Вне скоупа) — задача выполнима
   без чтения доков целиком; «вне скоупа» реально останавливает расползание.
4. **Разделение ролей по сессиям** (исполнитель ≠ критик ≠ приёмщик, свежий контекст
   на каждую) — критика свежими глазами находит то, что автор не видит; Handoff-ы
   zones-kanban это подтверждают (35 подтверждённых находок ревью на блоке 1).
5. **Handoff с отклонениями от ТЗ и граблями среды** — следующая сессия стартует с
   фактов, а не с археологии. Формат «что сделано / отклонения с причинами / среда /
   верификация» — образцовый.
6. **Готовые промпты сессий в SESSION.md** + актуализация промпта следующего блока
   критиком — конвейер самоподдерживается, владелец только копирует.
7. **«Зелёный билд ≠ работает»** — обязательная браузерная/стендовая верификация.
8. **Архивная дисциплина** и трассировка бриф → задачи.
9. **Каталожное ревью пост-приёмки** — взгляд «как дифф лёг в репо рядом со старым
   кодом» ловит класс проблем, который не видят ни исполнитель, ни критик блока
   (дубли хелперов, разъехавшиеся конвенции). REVIEW-файлы admin-ui-fixes — сильные.

## Что лишнее или проблемное (изменено)

1. **Тяжёлый дефолт процесса.** Оригинал: минимум 3 сессии на блок + ревью на каждый
   каталог + клинап = 5–6 сессий на любой блок, а потом полстраницы исключений
   «когда НЕ применяем». Если дефолту нужен список исключений — дефолт выбран
   неверно. *В эталоне:* режимы S/M/L; дефолт M (3 сессии), пост-приёмка — только
   L-блоки (публичные контракты, безопасность, миграции, критичный прод), эскалация
   точечная по блокам.
2. **Пересечение критика и каталожного ревью.** Гайд сам оправдывается, что
   пост-приёмка «не дубль» рефакторинг-сессии — но обе смотрят дифф блока, обе ищут
   упрощения и пробелы тестов. На M-блоках это двойная оплата одной работы.
   *В эталоне:* на M критик — единственное ревью; каталожный взгляд («дубли со
   старым кодом, конвенции каталога») включён в его чек-лист; отдельные каталожные
   ревью остаются только в L, где независимость взгляда оправдывает цену.
3. **Статусы в двух местах.** Легенда ⬜🔄✅♻️🏁 в §4 плюс трекер в SESSION.md — два
   источника, которые надо синхронизировать; ♻️ («рефакторинг готов») — статус роли,
   а не задачи, и живёт не там. *В эталоне:* задачи — ⬜🔄✅ в §4; роли — только в
   трекере SESSION.md; блок — ⬜🔄✅🏁. Каждый факт живёт в одном месте.
4. **`memory/` не в git.** Артефакт полирепо-структуры arealapp, а не решение: история
   решений и Handoff-ов не версионируется, нет бэкапа, нельзя связать правку бэклога
   с коммитом кода. *В эталоне:* доки и бэклоги — в git всегда.
5. **Имена моделей и даты сверки захардкожены в гайде и промптах** («Opus 5 high,
   сверено 2026-07-28») — устаревает за месяц, разъезжается по десяткам SESSION.md.
   *В эталоне:* промпты ссылаются на роль и уровень («критик, уровень review»),
   маппинг роль → модель/эффорт — один сменный листок `MODELS.md`.
6. **CHAIN.md как отдельная механика.** Приём «финальным сообщением выведи промпт
   следующего шага» хорош, но отдельный файл-раннер дублирует SESSION.md.
   *В эталоне:* правило встроено в каждый промпт SESSION.md; отдельный файл не нужен.
7. **Дублирование фактов** между §6 техконтекста и «Контекстом» ТЗ — со временем
   дрейфует (в ZK §6 разросся до внутренностей пяти подсистем). *В эталоне:* правило
   адресности — факт двух и более задач → §6, факт одной задачи → её ТЗ.
8. **Секреты в Handoff.** В реальном Handoff zones-kanban лежат пароли тест-юзеров
   открытым текстом. Для доков вне git это терпимо, в git — нет. *В эталоне:*
   инвариант 11 — значения только в `memory/secrets/` (в `.gitignore`) или env;
   в доках — ссылка/имя переменной; pre-commit-хук `memory/process/hooks/pre-commit`
   блокирует staged-файлы из `secrets/` и секрето-подобные строки в диффе.

## Чего не хватало (добавлено)

1. **Протокола бриф-интервью.** Оригинал: «владелец пишет бриф → Claude превращает
   в бэклог», открытые вопросы закрываются молчаливыми решениями составителя.
   Качество бэклога целиком зависит от полноты брифа, а полнота ничем не
   проверяется. *Добавлено:* `BRIEF-GUIDE.md` — раунды конкретизирующих вопросов
   (с вариантами, рекомендацией и дефолтом) по чек-листу 11 областей, до полной
   ясности; выход — подтверждённое владельцем резюме понимания. Бэклог по
   неподтверждённому резюме не строится.
2. **Секции «Тесты» в ТЗ.** Тесты появлялись как находки критика — задним числом.
   *Добавлено:* обязательная секция в шаблоне задачи: тест — часть задачи.
3. **Судьбы хвостов.** Хвосты записывались в §4 и повисали навсегда («кандидаты
   после MVP — решает владелец» без механизма решения). *Добавлено:* поле «судьба»
   (новый бэклог / блок N / принятый долг / отклонено); архивировать бэклог с
   необсуждёнными хвостами нельзя; бесхозные хвосты переезжают в STATE.md.
4. **STATE.md — статус проекта над бэклогами.** В оригинале «что сейчас активно и
   что было» восстанавливается листингом каталогов. *Добавлено:* один файл — активные
   бэклоги, история закрытых, хвосты-кандидаты.
5. **Процедуры изменения решения Р-*.** Прецедент в оригинале есть («решение
   владельца 2026-07-28» в тексте гайда), формата нет. *Добавлено:* запись в
   `memory/decisions/`, зачёркивание в §2 со ссылкой, актуализация незакрытых ТЗ.
6. **Плана отката.** Деплой описан, откат — нет. *Добавлено:* строка отката в
   промпте деплоящей сессии (образ/revert/миграция down).
7. **Явного лайт-режима.** «Одноразовая правка бэклога не требует» — а что требует,
   не сказано. *Добавлено:* режим S с критерием («описание короче, чем был бы
   бэклог») и форматом (одна сессия либо один файл задачи).

## Соответствие: оригинал → эталон

| Оригинал | Эталон |
|---|---|
| BACKLOG-GUIDE.md (всё в одном) | PROCESS (инварианты) + BRIEF-GUIDE + BACKLOG-GUIDE |
| Конвейер: рабочая → рефакторинг → приёмка → ревью×каталоги → клинап (всегда) | M: исполнитель → критик → приёмка; L: + пост-приёмка |
| Статусы ⬜🔄✅♻️🏁 в §4 + трекер | Задачи ⬜🔄✅ (§4), роли (трекер), блок ⬜🔄✅🏁 |
| docs вне git | docs в git |
| Модели в заголовках промптов | Роли в промптах, модели в MODELS.md |
| CHAIN.md | Правило «выведи следующий промпт» в каждом промпте |
| Бриф → сразу бэклог | Бриф → интервью до ясности → резюме → бэклог |
| Хвосты копятся в §4 | Хвосты с судьбой; сироты — в STATE.md |
| — | Секция «Тесты» в ТЗ, запрет секретов (`memory/secrets/` + pre-commit-гвард), план отката, STATE.md, decisions-процедура |
