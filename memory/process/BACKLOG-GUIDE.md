# Как вести бэклоги (эталонный гайд)

Единый паттерн многосессионных бэклогов. Читать перед тем, как заводить бэклог или
брать задачу из существующего. Инварианты — `PROCESS.md`; этап до бэклога —
`BRIEF-GUIDE.md`; шаблоны файлов — `templates/`; заполненный пример — `example/`;
проектные отличия (полирепо, команды верификации, деплой-грабли, применимость CI) —
`PROJECT.md` проекта, если заведён. Стек по умолчанию: Go (бэкенд) + Vue 3 SPA (фронт);
для другого стека меняются только команды верификации.

## Когда заводить бэклог

Бэклог нужен, когда работа не помещается в одну сессию: несколько блоков, зависимые
задачи, больше одного репо/каталога. **Мелочь (режим S) бэклога не требует** — одна
сессия делает и верифицирует; при неуверенности — один файл задачи по
`templates/task.md`, без каталога. Признак S: описание короче, чем был бы бэклог.

## Где что лежит

```
memory/backlog/<инициатива>/          # активный бэклог
├── 00-backlog.md                   # индекс — единственный источник статусов
├── <инициатива>-brief.md           # бриф + резюме бриф-интервью
└── block-N-<тема>/
    ├── SESSION.md                  # цель, трекер, промпты, Handoff, итоги
    ├── <ID>-NN-<слаг>.md           # ТЗ одной задачи
    └── REVIEW-<каталог>.md         # только L-блоки: каталожное ревью
```

- **Всё в git.** Доки и бэклоги коммитятся так же, как код: история решений и
  Handoff-ов — часть проекта. Правки бэклога сессия коммитит вместе со своим выходом.
- **Закрытый бэклог целиком уезжает в `memory/archive/`** + строка в `memory/STATE.md`.
  `memory/backlog/` держит только активное.
- ID-префикс инициативы — короткий и свой (`AV` — avatar-upload, `NT` — notifications).
- **Секреты в доки не пишутся никогда** (инвариант 11 PROCESS.md): ни паролей
  тест-юзеров, ни токенов, ни DSN с кредами. Значения — в `memory/secrets/`
  (каталог в `.gitignore`, версионируется только его README) либо в env; в
  Handoff — ссылка `memory/secrets/<файл>.md` или имя переменной. Гвард от
  случайного коммита — pre-commit-хук `memory/process/hooks/pre-commit` (блокирует
  staged-файлы из `secrets/` и секрето-подобные строки в диффе); в свежем клоне
  включить: `git config core.hooksPath memory/process/hooks`.

## Файл индекса `00-backlog.md`

Секции по порядку (шаблон — `templates/00-backlog.md`):

- **Шапка-статус** (blockquote): выполнено/в работе, что осталось; при закрытии —
  итог и пометка «в архив».
- **§1 Цель** — 3–5 строк: что, для кого, как выглядит успех. Режим процесса
  (S/M/L; блоки-исключения — пометкой в §4).
- **§2 Зафиксированные решения** — `Р-1, Р-2, …` — конституция бэклога. Сюда же
  ответы на открытые вопросы брифа (с источником: бриф / раунд интервью / дефолт).
  Рабочие сессии §2 не пересматривают. Изменение — только владельцем: старое
  решение зачёркивается с датой и ссылкой на запись в `memory/decisions/`.
- **§3 Матрица прав** — только если инициатива трогает роли/доступ (иначе пропустить).
- **§4 Блоки и задачи** — таблица: `Блок | Задача (ID + название) | Файл | Зависит
  от | Статус`. Статусы задач: **⬜ не начата · 🔄 в работе · ✅ готова**. Статус
  блока — строка-итог под таблицей блока либо колонка «Блок»: **⬜ → 🔄 → ✅ принят →
  🏁 закрыт**. Роли внутри блока отмечаются ТОЛЬКО в трекере его SESSION.md — здесь
  не дублировать (два источника статусов = рассинхрон). Ниже таблицы — трассировка
  бриф→задачи, список «после MVP» и «Хвосты» (см. ниже).
- **§5 Протокол** — одна строка-ссылка на этот гайд + отклонения, если есть
  (например «блок 2 — L: трогает публичный API»).
- **§6 Технический контекст** — факты, нужные **двум и более** задачам (пути, ручки,
  схемы, грабли среды). Факт одной задачи живёт в её ТЗ, не здесь: дублирование —
  это дрейф.

## Файл задачи `<ID>-NN-<слаг>.md`

Шаблон — `templates/task.md`:

```
# <ID>-NN — Короткое название (бэкенд/фронт)

Блок N · MVP|после MVP · Репо/каталог · Зависит от: <ID>|— · Роли: <кто>

## Контекст (что уже есть)   — факты кода для ЭТОЙ задачи: файлы, функции, конвенции
## Задача                    — нумерованные конкретные шаги
## Тесты                     — какие тесты пишутся в этой задаче (не «потом»)
## Критерии приёмки          — проверяемые условия + команды верификации
## Вне скоупа                — что НЕ делаем (граница против расползания)
```

Цель — самодостаточность: сессия выполняет задачу, не читая живые доки целиком.
Секция «Тесты» обязательна: тест — часть задачи, а не находка критика.

## Файл блока `SESSION.md`

Шаблон — `templates/SESSION.md`. Порядок секций:

1. **Цель блока** — первой строкой, 1–2 строки: что блок даёт и зачем.
2. **Трекер** — единственное место статусов ролей блока:
   `Сессии: исполнитель ⬜ · критик ⬜ · приёмка ⬜` (+ в L: `ревью <каталог> ⬜ …
   · клинап ⬜` — каталоги названы явно, по факту коммитов Handoff-а). Все ✅ →
   блок 🏁 в §4.
3. **Промпты сессий** — по одному ```-блоку на роль (исполнитель, критик, приёмка;
   в L — ревью по каталогу и клинап). Заголовок промпта несёт роль, уровень
   и вписанные составителем из `MODELS.md` актуальные модель/эффорт («критик —
   уровень review · Opus 5 · effort xhigh»); триггер-слова (`ultrathink`,
   `ultracode`) — прямо в команде внутри ```-блока. Смена поколения моделей =
   правка `MODELS.md` и заголовков незакрытых блоков активных бэклогов.
   Внутри ```-блока — ТОЧНАЯ slash-команда роли (`/worker <слаг> <N>` и т.д.):
   общая часть промпта живёт в `.claude/commands/` (см. `CLAUDE-CODE.md`),
   дублировать её в SESSION.md нельзя — два источника разъезжаются. Под командой —
   список «Блок-специфика»: среда, порядок/факты задач, затронутые доки и
   отклонения от generic-роли (S/L-режим, «НЕ деплоить», другой следующий шаг).
   Каждая роль в финале называет команду следующей сессии — конвейер
   самоподдерживается, владелец только копирует.
4. **Handoff** (заполняет исполнитель): коммиты (репо + хеш + ветка), что сделано
   по задачам, **отклонения от ТЗ с причинами**, грабли среды, чем верифицировано.
5. **Итоги критика**: находки, что упрощено, обновлённые доки, статус промпта
   следующего блока.
6. **Приёмка**: вердикт «принято»/возврат, что проверено в реальной среде, деплой.
7. **Итоги пост-приёмки** (только L): что из REVIEW-рекомендаций сделано /
   отклонено (с причиной) / ушло в хвосты; деплой и прод-смоук.

## Протокол сессий

Конвейер блока (M): `исполнитель → критик → приёмка → блок закрыт (🏁)`.
Свежий контекст на каждую роль; исполнитель не принимает сам себя.

- **Исполнитель**: задачи строго по порядку ID, по одной; §2 не трогает; ТЗ
  противоречит коду → минимальное локальное решение + запись в Handoff, без
  перепроектирования; новых библиотек и абстракций сверх ТЗ не вводит. По
  завершении: верификация, статусы §4, Handoff. К следующему блоку не переходит.
- **Критик**: читает Handoff + дифф блока (по хешам из Handoff); сверяет с
  критериями каждого ТЗ; ревью корректности → упрощение/реюз → добить тесты →
  короткие правки живых доков (только затронутые секции) → **актуализировать промпт
  следующего блока** по фактическому состоянию кода. Фич не добавляет; находка
  крупнее правки — в хвосты.
- **Приёмка**: сверяет блок с критериями всех ТЗ, гоняет верификацию в реальной
  среде (браузер, живой стенд) и весь накопленный e2e-набор (регрессия); новые
  сценарии сохраняет в `e2e/`; вердикт в SESSION.md. Принято → деплой по стандарту
  проекта + смоук (в L деплой уезжает в клинап). Возврат → список конкретных
  расхождений исполнителю, не чинит сама.

**Пост-приёмка (только L-блоки)** — после вердикта «принято», до открытия
следующего блока: по одной независимой ревью-сессии на каждый каталог, затронутый
коммитами блока. Смотрит уже принятый дифф глазами каталога: дубли с существующим
кодом, разъехавшиеся конвенции, пробелы покрытия. Результат — `REVIEW-<каталог>.md`:
находки по убыванию важности, каждая с файл:строка, рекомендацией и вердиктом
**«клинап · хвост · не делаем + почему»**. Код ревью не меняет. Затем одна
клинап-сессия выполняет все «клинап»-вердикты, деплоит блок на прод, пишет «Итоги
пост-приёмки», ставит 🏁. Каталог без коммитов блока в ревью не попадает; ревью
«на всякий случай» не проводим.

**Контекст-диета (обязательно)**: сессия читает ТОЛЬКО `00-backlog.md` →
`block-N/*` → файлы кода из ТЗ. Живые доки — точечный grep при пробеле.

**Верификация перед завершением (обязательна, «зелёный билд ≠ работает»)**:
- Go: `go build ./... && go test ./...` из корня модуля.
- Vue 3 SPA: `pnpm build` (с vue-tsc) + юнит-тесты (Vitest) + **проверка
  интерактива в реальном браузере** (метод фиксируется в доках проекта один раз).
- **CI обязателен**: каждый репо кода держит CI (шаблоны — `templates/ci-go.yml`,
  `ci-web.yml`; заводится первым бэклогом проекта). Красный CI = блок не готов,
  что бы ни писал Handoff. Проект без CI-раннера фиксирует это в `PROJECT.md` —
  тогда строгость держат верификация сессий и роли критика/приёмки.
- **Браузерные сценарии — накопительные**: сценарии приёмки сохраняются в репо
  фронта (каталог `e2e/`), а не выбрасываются; приёмка блока N гоняет ВЕСЬ
  накопленный набор (регрессия прошлых блоков), не только сценарии своего блока.
- Прод-деплой всегда заканчивается смоуком: главный сценарий руками/скриптом.

## Git

- Каждая задача — отдельный коммит; сообщение начинается с ID (`AV-01: …`).
- Блок можно вести в ветке `<id>-block-N-<тема>`; мёрж — после вердикта приёмки.
  Малые блоки допустимо вести в main — решает владелец в §5.
- Правки доков/бэклога — коммитом той сессии, которая их сделала.
- План отката прод-деплоя — одна строка в промпте деплоящей сессии (что откатываем
  и как: предыдущий образ, `git revert`, миграция down).

## Хвосты

Хвост — находка крупнее текущей задачи (идея, долг, не-баг). Хвосты не делаются
походя — записываются в §4 «Хвосты» с полем «судьба», которое назначает владелец:
**в новый бэклог · сделать в блоке N · принятый долг (не делаем) · отклонено**.
При закрытии бэклога хвосты без судьбы выносятся в `memory/STATE.md` — бэклог нельзя
архивировать с висящими необсуждёнными хвостами.

## Закрытие бэклога (DoD инициативы)

Бэклог закрыт, когда выполнено ВСЁ: все блоки 🏁; у всех хвостов §4 назначена
судьба (⏳ не осталось); живые доки актуализированы по фактическому состоянию;
CI всех затронутых репо зелёный (где применим — `PROJECT.md`); e2e-набор пополнен
сценариями приёмок;
шапка-статус `00-backlog.md` — итог и дата; запись в `memory/STATE.md` (строка в
«Закрытые», бесхозные хвосты — в его таблицу); каталог целиком → `memory/archive/`.
Финальное сообщение владельцу: итог одной строкой + предложение следующего шага.

## Изменение зафиксированного решения

Только владелец. Процедура: запись в `memory/decisions/<тема>.md` (дата, Р-N: было →
стало, причина, что затронуто) → правка §2 (старое зачёркнуто со ссылкой) →
затронутые невыполненные ТЗ актуализируются той же сессией. Выполненные блоки не
переделываются молча — если изменение их ломает, это новая задача/блок.

## Чек-лист «завести новый бэклог»

1. Бриф-интервью пройдено, резюме подтверждено владельцем (`BRIEF-GUIDE.md`).
2. `memory/backlog/<инициатива>/00-backlog.md`: §1–§6, решения Р-* из резюме,
   блоки с зависимостями, статусы ⬜, режим S/M/L (+ L-пометки на блоках).
3. По файлу на задачу (`<ID>-NN-*.md`) по шаблону — с секцией «Тесты» и «Вне скоупа».
4. `SESSION.md` в каждом блоке: цель первой строкой, трекер, промпты ролей
   (в L — + ревью по каталогам и клинап), пустые секции Handoff/Итоги/Приёмка.
5. Проверить контекст-диету: исполнитель первого блока может стартовать, прочитав
   только индекс + свой блок. Если ему пришлось бы искать — донести факты в ТЗ/§6.
6. Закоммитить бэклог. Выдать владельцу команду исполнителя первого блока
   (`/worker <слаг> 1`).
