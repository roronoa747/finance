# Правила проекта

Проект ведётся по процессному фреймворку из `memory/process/`. Стек: React 19,
TypeScript, Vite, Tailwind CSS 4, Zustand, Supabase.

## Как работает процесс (карта чтения)

- `memory/process/PROCESS.md` — инварианты и конвейер (прочитать первым).
- `memory/process/BRIEF-GUIDE.md` — этап брифа.
- `memory/process/BACKLOG-GUIDE.md` — ведение бэклога и протокол сессий.
- `memory/process/MODELS.md` — какая модель/эффорт на какую роль.
- `memory/process/CLAUDE-CODE.md` — интеграция с примитивами Claude Code; slash-команды
  ролей готовы в `.claude/commands/` (`/brief`, `/backlog`, `/worker`, `/critic`,
  `/ux`, `/accept`, `/dir-review`, `/cleanup`) — конвейер запускается ими.
- `memory/process/templates/` — шаблоны артефактов (включая CI: `ci-web.yml`);
- `memory/STATE.md` — текущий статус проекта: с него начинается любая сессия,
  не знающая контекста.

## Жёсткие правила (нарушать нельзя)

1. **Новая инициатива начинается с брифа.** Когда владелец описывает новый блок
   работ — НЕ бросаться делать и НЕ строить бэклог сразу. Сначала бриф-интервью по
   `memory/process/BRIEF-GUIDE.md`: разведка кода → **раунды конкретизирующих вопросов
   (AskUserQuestion: варианты + рекомендация + дефолт) до тех пор, пока суть блока
   работ не ясна полностью** → резюме понимания → подтверждение владельца → только
   потом бэклог.
2. **Решения §2 бэклога не пересматриваются** рабочими сессиями. Противоречие ТЗ
   и кода → минимальное локальное решение + запись в Handoff.
3. **Контекст-диета**: в рамках бэклога читать только индекс → свой блок → файлы
   из ТЗ; живые доки — точечным grep-ом.
4. **Одна сессия — одна роль** (исполнитель / критик / приёмка). Свою роль узнай
   из промпта; исполнитель не принимает сам себя и не переходит к следующему блоку.
5. **Верификация реальностью** перед отметкой «готово»:
   `npm run typecheck` (`tsc -b --noEmit`), `npm run build` (`vite build`), запуск
   целевых тестов (`npm run test:num`, `npm run test:screens` и т.д.) + проверка
   в браузере. Зелёный билд ≠ работает.
6. **Доменные инварианты финансов**:
   - **Деньги — целые числа** (тенге / минорные единицы). Никаких дробей в состоянии.
   - **Все числа считает `src/lib/finance.ts`**. Моделям считать деньги не доверяем.
   - **Цвет берётся только из токена** в `src/index.css` (у каждого токена есть пара для тёмной темы).
7. **Всё письменно**: статусы — в `00-backlog.md` §4, факты и отклонения — в
   Handoff, статус проекта — в `memory/STATE.md`.
8. **Секреты НИКОГДА не попадают в git** (инвариант 11 PROCESS.md). Значения —
   только в `memory/secrets/` (в `.gitignore`) или env; в доки — имя переменной или
   ссылка на файл в `secrets/`. Pre-commit-хук `memory/process/hooks/pre-commit` блокирует
   нарушения — не обходить его `--no-verify`; если хук не включён
   (свежий клон) — включить: `git config core.hooksPath memory/process/hooks`.
9. **Задача = коммит** (сообщение начинается с ID). Доки и бэклоги коммитятся.
10. Абстракции «на будущее» не заводить; находка крупнее задачи — хвост в §4,
    а не попутная переделка.
11. **Режим наставника — включён всегда.** Владелец осваивает фреймворк на
    реальном проекте: перед неочевидным шагом — одна строка «что делаю и по
    какому правилу»; в конце каждой сессии — короткий разбор (3–5 строк): что
    произошло в терминах процесса, какая роль/правило сработали, на что владельцу
    посмотреть; на вопрос «почему так» отвечать со ссылкой на конкретный раздел
    гайда. Разборы короткие — обучение не удлиняет конвейер.
    **Финал сессии — порядок (владелец, 2026-10-03):** сначала «Что сделано» — простыми
    словами, что изменилось для приложения и для владельца (коммиты, правки, проверки), затем
    разбор наставника, и только последней строкой — следующий шаг (команда).
12. **Правила интерфейса (владелец, 2026-09-27)** — проверяются исполнителем, критиком и приёмкой
    на каждом экране, наравне с `DESIGN.md`:
    - **Одно действие за раз.** Экран или карточка предлагает одно главное действие; главная кнопка —
      одна, брендовая (`--brand`), её видно без чтения; второстепенные — тихие (`secondary`,
      `ghost`). Путь к любому действию — не больше двух нажатий, нажатие ведёт туда, куда ждёшь.
    - **Смысловой флоу (владелец, 2026-10-05).** Действие живёт у своего предмета: небольшой кнопкой
      в строке или карточке того, к чему относится («Оплатил» — у платежа, «Отложил» — у цели,
      «Пришла» — у зарплаты; сделано — ✓ у суммы в той же строке), а не отдельной крупной карточкой наверху или внизу экрана. Вопрос для
      проверки: «к чему это действие?» — если предмет уже есть на экране, кнопка стоит в нём. Позвать
      к действию издалека — точкой или счётчиком (на вкладке, сегменте, заголовке раздела), не блоком.
      Крупная кнопка во всю ширину — только подтверждение в листе или форме и пустой экран, где
      больше ничего нет (первый шаг).
    - **Текста минимум.** Заголовок 1–3 слова, под ним одна строка. Пояснение длиннее строки — в
      подсказку `Hint` (?) рядом с текстом, а лучше убрать: понятно должно быть визуально (фото, цифра,
      полоса), не абзацем. Механика (выписка, PDF, банк) — не в заголовках.
    - **Образ вместо текста.** Мечты и желания — с фото; процент и сумма — крупно, подпись — коротко.
    - **Нет шумных цифр (владелец, 2026-10-08).** На экране одна крупная цифра у предмета, остальные —
      в предмете (куда нажимаешь); второстепенные даты и проценты — в листе предмета. Ничего не теряется —
      число переезжает, а не исчезает.
    - **Сложное — скрыто.** Калькуляторы, графики, таблицы и расчёты — за «подробнее», каруселью или
      листом, по умолчанию свёрнуты; главный поток их не показывает.
    - В Handoff по каждому экрану: главное действие и у какого предмета оно стоит, что ушло в
      подсказку, что скрыто.
